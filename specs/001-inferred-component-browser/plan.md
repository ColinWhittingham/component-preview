## Summary

Build a Chrome Manifest V3 extension that analyses any web page to identify UI components (using React/Vue/Angular runtime metadata when available, semantic HTML otherwise), captures isolated snapshots of each component, stores them locally, and serves them through a predictable URL scheme with a Storybook-like browser interface. The extension UI is a single-page application served at `chrome-extension://[ID]/components/` that handles both the component index and individual component views, with query string-driven prop overrides.

---

## Technical Context

**Language/Version**: JavaScript (ES2020) + TypeScript 5.x for type safety during development

**Primary Dependencies**:
- Chrome Extension APIs (MV3): `chrome.scripting`, `chrome.storage`, `chrome.runtime`, `chrome.tabs`, `chrome.action`
- Vite (bundler) — fast builds, handles multi-entry extension structure
- No runtime UI framework — vanilla JS for the extension pages to avoid bundling overhead and CSP complications in extension pages

**Storage**:
- `chrome.storage.local` — component index metadata (PageRecord, ComponentRecord)
- IndexedDB (via native browser API) — component snapshots (HTML + CSS strings)

**Testing**: Vitest (unit tests for analyser and slug logic); Playwright (end-to-end extension loading and URL routing)

**Target Platform**: Chrome 116+, Manifest V3, Windows / Mac / Linux

**Project Type**: Browser extension (Chrome)

**Performance Goals**: Component index available within 5 seconds of activation (SC-001); individual component page loads in under 2 seconds

**Constraints**:
- MV3 prohibits `eval()` and remote script execution — all logic must be bundled locally
- Content Security Policy (CSP) on extension pages: no inline scripts, no external resources at runtime
- Service worker lifetime is ephemeral in MV3 — all persistent state goes to storage, not SW memory

**Scale/Scope**: Single-user local extension. No network calls to external services. Analysis runs per-tab on demand.
